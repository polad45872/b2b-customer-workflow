# 多行业 B2B 潜客检索引擎

基于产品或服务和目标客户画像，在指定中国城市发现企业潜客，核验企业主体、实际经营地域及业务匹配，交付可追溯的企业名单、来源证据和覆盖核验表。

本项目以 Skill 形式供宿主 Agent 使用。Agent 负责实际网页检索、读取证据和业务判断；Python 脚本负责配置校验、计划、批次、去重记录、状态门禁及交付校验。仅运行脚本不会自动完成互联网检索。

## 1. 适用范围与能力边界

适用于设备、企业软件、专业服务等 B2B 获客场景。通过行业配置更换我方产品、目标客户角色、业务场景、关键词和匹配规则，无需把所有行业写进核心脚本。

支持：

- 城市级企业发现、主体解析、地域核验、全局去重和业务匹配。
- 根据企业线索优先发现，结合覆盖补漏和同类企业扩展。
- 批次推进、候选结转、状态恢复、冻结及全量重算。
- 企业名单、FINAL 证据包及覆盖核验表的成套交付。
- 可选补全核心产品、客户类型、下游行业、下游客户和竞争对手。

当前版本不包含企查查导入或回填、经营及采购估算、网页前端、API 服务、跨任务客户数据库、CRM 集成或计费功能。保留在表头中的登记及销售字段不代表系统会自动补齐或写入外部系统。

`FINAL` 表示符合本任务客户画像的合格潜客，不代表已确认预算、采购意向或采购金额。覆盖完成及增量收敛是本次检索的停止依据，不承诺找到城市中所有企业。

## 2. 运行环境与安装

- Python 3.12。
- 依赖：`openpyxl>=3.1,<4`、`PyYAML>=6,<7`，以根目录 `requirements.txt` 为准。
- 宿主 Agent 具备网页检索、网页读取和本地脚本执行能力。
- 可写的外部任务目录，用于保存状态、证据、日志和交付物。

将本包整体放入宿主 Agent 的 Skills 目录，目录命名为 `b2b-customer-workflow`，保留内部结构。安装依赖时传入本包的实际路径：

```text
python -m pip install -r <引擎根目录>/requirements.txt
```

执行各脚本时使用实际绝对路径；不要假设当前目录就是 Skill 目录。安装目录保存代码和规则，运行目录保存任务数据。

## 3. 快速开始

启动前明确四项输入：目标城市、我方产品或服务、目标客户画像、交付范围。画像应说明哪些企业角色和业务场景可能需要我方产品，以及需要排除的企业。

可向宿主 Agent 提交：

```text
使用 $b2b-customer-workflow。
目标城市：苏州市。
我方产品或服务：……
目标客户角色和业务场景：……
排除条件：……
交付范围：企业名单 Excel、FINAL 证据包、覆盖核验 Excel。
请先依据这些信息准备行业配置，再执行检索与核验。
```

需要后续分析时，在交付范围中增加“补全企业业务信息及竞争对手”。已有明确配置和会话信息时可直接使用；只给城市而没有产品及画像时，需要先补齐检索范围。

设备、软件及服务示例只用于说明配置结构，需按实际业务调整并确认，不能直接当作真实获客策略。

## 5. 行业配置：决定搜谁、为什么入选

配置整包包括画像、词库、扩展链、字段权限和执行策略。主要需要定义：

- 我方产品服务、目标行业、客户角色与业务场景。
- 企业纳入、排除及业务匹配规则。
- 关键词族、用途适配、覆盖别名及深化策略。
- 扩展特征链和允许使用的来源类型。
- 输出表头、阶段字段权限及策略档位。

`profile.assets` 的相对路径以配置文件所在目录为基准解析。复制示例到外部配置目录时，应同步处理所引用资产的路径。

配置与执行版本通过文件摘要绑定到城市任务。任务运行后修改绑定配置会被阻断；需恢复原版本，或另建任务。不同画像、词库和策略不能混入同一任务，旧版行业状态也不能直接续跑本版。

只读校验与预览示例：

```text
python <引擎根目录>/search-skill/scripts/config_lint.py --profile <行业配置.json>
python <引擎根目录>/search-skill/scripts/b2b_profile_control.py validate --profile <行业配置.json>
python <引擎根目录>/search-skill/scripts/b2b_profile_control.py preview --profile <行业配置.json> --city <城市>
```

## 6. 检索流程与核心模块

```text
明确画像 → 校验配置 → 准备空间与主表 → 初始化城市状态
→ 规划查询 → 网页发现 → 校验合并 → 候选入池与处置
→ 主体/地域/业务核验 → 同类扩展与覆盖补漏
→ 批次结转与累计复算 → 停止候选 → 冻结 → 全量重算 → 交付
```

| 模块 | 主要职责 |
|---|---|
| b2b_profile_control.py / config_lint.py | 配置校验、预览、城市空间及模板准备 |
| state_guard.py | 初始化主控令牌，保护正式状态写入 |
| workflow_orchestrator.py | 根据线索、历史产出及覆盖缺口规划下一动作 |
| batch_context_control.py | 批次上下文、发现登记及批次记录 |
| search_worker_control.py | 只读发现任务包、结果校验及合并 |
| search_stage_runner.py | 工作集核验、提交与批次推进 |
| expansion_control.py | 基于可追溯种子的同类企业扩展 |
| city_coverage_control.py | 城市累计覆盖、停止检查、冻结及重算 |
| final_delivery_control.py | 独立复核并导出交付物 |
| workflow-control/scripts/workflow.py | 可选分析阶段、字段锁及最终状态推进 |

详细命令顺序以执行流程为准，具体参数先查看对应脚本 `--help`。上述模块是受控接口，不应以手工修改状态 JSON 的方式替代正式提交。

发现优先沿具体企业产品、场景、项目及来源名单推进；基础词库用于锚定范围与审计。每条查询保留实际访问网址、检查数量及终止原因，零结果和访问失败也要记录。所有发现线索都有处置记录，扩展所得企业必须独立核验。

主控负责主体解析、全局去重、语义核验和正式状态写入。只有会话授权允许委派时才使用只读研究 Worker；不可委派时记录实际降级原因，并按相同结果协议执行。Worker 结果不能直接成为 FINAL，主控令牌也不能进入 Worker 包。

## 7. 企业入选与证据口径

入选至少需要企业主体、目标城市实际经营地、业务事实及画像匹配有来源支持，并完成去重。官网地址必须核验归属，无法确认时留空。

分别记录业务事实、客户匹配推断和已知采购需求。供应商、竞争对手或合作关系本身不能证明需要我方产品；渠道和合作伙伴是否纳入由配置决定。未知采购意向不妨碍业务匹配成立的企业入选。

身份或地域歧义进行定向补查；未知信息保留未知。候选池、查询记录、异常及原始证据在导出后继续保留。运行中按候选 ID 和计数报告进度，最终企业交付物提供企业名称。

## 8. 停止条件与交付门禁

停止依据是城市累计覆盖与新增企业收敛，不能以名单数量、单批结束或网页访问受限替代完成判断。

当前默认策略：

| 策略 | 每轮最少有效查询 | 独立零新增轮次 | 建议查询预算 | 覆盖矩阵完成率 |
|---|---:|---:|---:|---:|
| standard | 8 | 3 | 10 | 100% |
| strict | 12 | 4 | 16 | 100% |
| light | 8 | 3 | 8 | 100% |

实际运行以任务绑定的策略资产为准；低于核心下限的整包配置会被拒绝。

达到 `STOP_CANDIDATE` 后先执行 `freeze`，再执行 `recalculate`。覆盖、收敛和 `search_complete` 全量重算通过且无差异后，才能传入城市状态、冻结清单及正式快照执行 `deliver`。导出器会独立只读复算，不接受手写完成标志。

## 9. 交付物与字段权限

| 产物 | 内容 |
|---|---|
| 企业主表 Excel | 本次 FINAL 企业与允许导出的业务字段 |
| FINAL 企业证据包 JSON | 企业身份、发现来源、地域和业务匹配依据、原始证据及扩展追溯 |
| 城市覆盖核验 Excel | 区县、角色、行业、词族、来源、查询执行及收敛和扩展审计 |
| 交付清单 | 三项正式产物的文件摘要及交付校验信息 |

主表与证据包的企业集合必须一致。FOLLOWUP、EXCLUDED、CARRYOVER 等不进入最终名单，仍保留在工作记录中。

默认主表 15 列：序号、企业名称、官网地址、具体地址、成立时间、注册资金/万、参保人数、交付的核心产品、客户类型、下游行业、下游客户（企业交付物卖给哪些企业）、客户的竞争对手、CRM录入（是否）、归属区域、归属销售。

检索阶段只填写前三列。序号使用已分配企业 ID，导出时不重新编号；默认第一行为表头、第二行为模板说明，数据从第三行开始。其他表头可按配置追加，必须与绑定模板及权限一致。后续阶段按字段名授权更新，不依赖列字母。

## 10. 可选业务分析

仅交付检索结果时：

```text
SEARCH_RUNNING → SEARCH_DONE → DELIVERY_READY → DONE
```

需要业务补全及竞争对手分析时：

```text
SEARCH_DONE → INFERENCE_RUNNING → INFERENCE_DONE → BASE_FIELDS_LOCKED
→ COMPETITOR_SEARCH_RUNNING → COMPETITOR_SEARCH_DONE → DELIVERY_READY → DONE
```

业务推断阶段填写核心产品、客户类型、下游行业和下游客户；竞争对手阶段填写客户的竞争对手。主控领取批次、校验并保存 Agent 提交的结果 JSON，脚本不自动生成业务结论。

每阶段的企业 ID 集合须与已核验名单一致，全部完成真实提交后才能推进。未知业务信息可明确填“未知”；分析结论需有证据。主体冲突必须记录并解决，不能用自报的冲突数量绕过门禁。

分析后的导出需要提供 `--workflow-state`。推进 `DONE` 时提交正式交付清单，门禁复核冻结链、文件摘要、企业集合、字段、证据及覆盖表内容。具体操作见后续工作流说明。

## 11. 续跑与故障处理

续跑使用原运行目录、原配置及原执行版本，先读取正式状态和待处理动作，再按编排器继续，不重新初始化覆盖状态或重复分配企业 ID。活动工作集需要提交或按规则处理后才能关闭批次，未开始核验的候选显式结转。

| 情况 | 处理方式 |
|---|---|
| 配置校验失败 | 检查资产路径、词库族、覆盖维度及字段权限；修复后重新校验 |
| 运行中摘要不匹配 | 恢复绑定版本，或为新配置建立独立任务 |
| 网页不可访问 | 保留失败与终止原因，尝试其他来源；不能记为覆盖完成 |
| 同名、别名或集团关系不清 | 主控核对主体并保留处置依据 |
| 零新增但仍不能停止 | 检查覆盖缺口、有效查询和独立轮次，而非增加完成标志 |
| 冻结重算或导出失败 | 依据门禁返回定位底层记录，修复后重新按正式流程检查 |
| 后续阶段无法推进 | 检查真实提交记录、企业 ID 集合、字段权限和未解决冲突 |

## 12. 维护与验证

代码、规则、配置和任务数据分开维护。更换行业优先修改配置；修改核心脚本或规则后，保留版本记录并重新验证相关路径。禁止将历史实验目录、旧模板和当前任务状态混用。

交付前应确认：配置整包校验通过；全部发现线索有处置；FINAL 主体、地域及业务证据齐全；覆盖与收敛通过冻结重算；主表和证据企业集合一致；三项产物和交付清单通过独立校验。静态配置校验不能代替真实网页检索及企业核验。

本 README 是项目总览；执行细节以链接的阶段规范、绑定配置和当前脚本帮助为准。维护时应同步更新功能边界、命令入口、字段权限、策略说明及交付结构。
